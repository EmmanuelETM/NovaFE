## 1. Visión general del sistema

### Objetivo

Construir un **servicio SaaS multi-tenant** que actúe como proveedor de servicios de facturación electrónica autorizado por la DGII (Modelo 2: certificados y firmas en infraestructura del proveedor), encapsulando toda la complejidad fiscal, criptográfica y de comunicación requerida por la normativa dominicana de facturación electrónica (e-CF).

### Actores del sistema

| Actor | Rol |
|---|---|
| **DGII** | Autoridad tributaria. Valida, acepta o rechaza los e-CF |
| **Emisor electrónico (cliente nuestro)** | Contribuyente autorizado que genera e-CF a través de nuestro SaaS |
| **Receptor electrónico** | Contribuyente que recibe e-CF de nuestros clientes (también expone endpoints B2B) |
| **Receptor no electrónico** | Consumidor final que recibe la representación impresa (RI) |
| **Nuestro SaaS** | Intermediario entre clientes y DGII; custodios de certificados P12 (Modelo 2) |

### Tipos de comprobantes soportados

| Código | Tipo | Enviar a DGII | Enviar a receptor | Aprobación comercial |
|---|---|---|---|---|
| 31 | Factura de Crédito Fiscal Electrónica | Sí | Sí | Sí |
| 32 | Factura de Consumo Electrónica | Sí (RFCE si < 250k) | Sí si ≥ 250k | No |
| 33 | Nota de Débito Electrónica | Sí | Sí | Sí |
| 34 | Nota de Crédito Electrónica | Sí | Sí | Sí |
| 41 | Comprobante Electrónico de Compras | Sí | No | No |
| 43 | Gastos Menores Electrónico | Sí | No | No |
| 44 | Regímenes Especiales Electrónico | Sí | Sí | Sí |
| 45 | Gubernamental Electrónico | Sí | No | Sí |
| 46 | Exportaciones Electrónico | Sí | No | No |
| 47 | Pagos al Exterior Electrónico | Sí | No | No |

**Nota sobre tipo 32:** Si `MontoTotal < DOP 250,000`, enviar solo el RFCE (resumen) a DGII; el XML completo se almacena localmente. Si `MontoTotal ≥ DOP 250,000`, enviar el XML completo a DGII por `/api/facturaselectronicas` Y además al receptor electrónico.

### Ambientes DGII

| Ambiente | Nombre | Propósito |
|---|---|---|
| TesteCF | Pre-certificación | Desarrollo libre e integración (60 días hábiles iniciales) |
| CerteCF | Certificación | Pruebas oficiales de certificación ante DGII |
| eCF | Producción | Emisión con validez fiscal real |

**URLs CerteCF (verbatim, verificadas contra PDF DGII mayo 2026):**
```
Autenticación:   https://eCF.dgii.gov.do/CerteCF/Autenticacion
Recepción:       https://eCF.dgii.gov.do/CerteCF/Recepcion
ConsultaResult:  https://eCF.dgii.gov.do/CerteCF/ConsultaResultado
RecepcionFC:     https://fc.dgii.gov.do/CerteCF/RecepcionFC
AprobComercial:  https://eCF.dgii.gov.do/CerteCF/AprobacionComercial
```

**Diferencia crítica entre ambientes:**
- CerteCF NO tiene los servicios: `consultaestado`, `consultatrackids`, `anulacionrangos`, `consultadirectorio`.
- Diseñar con lógica condicional por ambiente: si ambiente ≠ eCF, deshabilitar esos endpoints en el routing interno.
- Las secuencias en CerteCF tienen rango 1–10,000,000 por tipo y NO son reutilizables tras rechazo.

## 2. Módulo 1 — Autenticación y certificados digitales

### Descripción

Gestiona el ciclo de vida del certificado digital y el proceso de autenticación por semilla ante la DGII, produciendo el token JWT necesario para todos los demás web services. En Modelo 2 (SaaS), el certificado P12 del contribuyente reside en nuestro Vault — nunca en el sistema del cliente.

### Endpoints reales DGII (corregidos)

```
GET  /api/autenticacion/semilla            → XML con semilla (UUID + timestamp)
POST /api/autenticacion/validarsemilla     → Token JWT (expedición + expiración)
```

⚠️ **Diferencia crítica:** Los endpoints `/fe/autenticacion/api/semilla` y `/fe/autenticacion/api/validacioncertificado` son los que **nosotros exponemos** para que otros contribuyentes nos autentiquen cuando nos envían e-CF. Son paths distintos con estructura diferente (`/fe/` vs `/api/`). Ver Módulo 5.

### Requerimientos funcionales

**RF-01.1** — Cargar y almacenar el certificado digital `.p12` del contribuyente cifrado en Vault. El campo `SN` del certificado debe corresponder exactamente al RNC, cédula o pasaporte del propietario. **Validar este campo antes de cualquier operación de firma** — un certificado con `SN` incorrecto producirá rechazos silenciosos en DGII.

**RF-01.2** — Implementar el flujo de autenticación de dos pasos:
1. `GET /api/autenticacion/semilla` → obtener XML semilla (UUID + timestamp)
2. Firmar el XML semilla con SHA-256 usando el certificado del tenant
3. `POST /api/autenticacion/validarsemilla` → obtener token JWT con `FechaExpiracion`

**RF-01.3** — Gestionar el ciclo de vida del token con caché por tenant y ambiente:
- Almacenar en Redis con TTL = `FechaExpiracion` - 5 minutos (renovación proactiva)
- Si el token está por expirar durante una emisión en curso, renovar antes de continuar
- Nunca persistir el token en base de datos; siempre en caché efímera

**RF-01.4** — Multi-tenant estricto: aislamiento total de certificados y tokens entre tenants. Un error de autenticación de un tenant nunca afecta a otros.

**RF-01.5** — Registrar cada autenticación: `tenant_id`, `timestamp`, `ambiente`, `éxito/error`, `huella_certificado`.

**RF-01.6** — Alertar proactivamente cuando un certificado esté próximo a vencer (90, 30, 15, 7 días). Los certificados vencidos bloquean la emisión.

### Requerimientos no funcionales

- El P12 nunca se persiste fuera de Vault ni se transmite al cliente.
- El token nunca se almacena en texto plano; Redis con cifrado en reposo.
- Todas las llamadas usan HTTPS/TLS 1.2+ con validación del certificado del servidor DGII.
- Tiempo de obtención del token: < 2 segundos en condiciones normales.

### Entidades de datos

```
Certificado {
  id            UUID PRIMARY KEY,
  tenant_id     UUID NOT NULL REFERENCES tenants(id),
  rnc           VARCHAR(11) NOT NULL,
  vault_path    VARCHAR(255) NOT NULL,  -- ruta en Vault, nunca el P12
  huella_sha256 CHAR(64) NOT NULL,
  fecha_emision DATE NOT NULL,
  fecha_vencimiento DATE NOT NULL,
  ambiente      VARCHAR(10) NOT NULL,  -- testecf | certecf | ecf
  activo        BOOLEAN DEFAULT TRUE,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
}
-- TokenSession se gestiona solo en Redis, no en DB
```

## 3. Módulo 2 — Generación y validación de XML

### Descripción

Construye los documentos XML conformes a los XSD publicados por la DGII para cada tipo de operación, aplicando todas las reglas de obligatoriedad de campos según el tipo de comprobante. Este módulo es el corazón del dominio — sin dependencias HTTP/DGII, completamente testeable de forma aislada.

### Formatos XML implementados

| Etiqueta raíz | Nombre | Notas |
|---|---|---|
| `<ECF>` | Comprobante fiscal electrónico | Todos los tipos 31-47 |
| `<RFCE>` | Resumen Factura de Consumo | Solo tipo 32 < DOP 250,000 |
| `<ARECF>` | Acuse de Recibo | Firmado, retornado al emisor que nos envía |
| `<ACECF>` | Aprobación/Rechazo Comercial | Generado por el receptor tras revisión |
| `<ANECF>` | Anulación de e-NCF | Casing especial: `<RncEmisor>` (c minúscula) |

### Reglas de campos críticos

#### FechaVencimientoSecuencia
- **Presente** en: tipos 31, 33, 41, 43, 44, 45, 46, 47
- **Ausente** en: tipos 32 y 34 — estos tipos NO tienen fecha de vencimiento de secuencia
- Error común: incluirlo en tipo 32 o 34 produce rechazo en DGII

#### RNCComprador / RazonSocialComprador
- Obligatorio en tipos: 31, 33, 34, 44, 47
- **Tipo 32:** solo obligatorio si `MontoTotal ≥ DOP 250,000`; omitir si < 250,000
- En tipo 32 ≥ 250k el RNCComprador identifica al receptor al que se enviará el e-CF

#### MontoItem
- En todos los tipos, MontoItem ≥ 0
- **Excepción válida:** MontoItem = 0 en Notas de Crédito (tipo 34) que solo corrigen texto/descripción, sin afectar montos

#### TipoIngresos (campo exclusivo del RFCE)
- Solo existe en el `<RFCE>`, no en el `<ECF>` del tipo 32
- Valores válidos: 01 a 06 (tabla DGII)
- Campo obligatorio en el RFCE; el modelo de dominio debe tenerlo como campo propio

#### ANECF — casing de RncEmisor
- El ANECF usa `<RncEmisor>` (con 'c' minúscula)
- Todos los demás formatos usan `<RNCEmisor>` (todo en mayúsculas)
- El serializador debe usar el casing exacto por tipo de documento; no usar un campo único sin alias por formato

### Secciones del XML e-CF

#### Sección Encabezado — campos universales

| Campo XML | Descripción | Tipo | Decimales |
|---|---|---|---|
| `<Version>` | Versión del formato | NUM | — |
| `<ENCFElectronico>` | e-NCF (13 pos: E + tipo 2d + secuencial 10d) | ALFANUM | — |
| `<FechaVencimientoSecuencia>` | Vencimiento (AUSENTE en tipos 32 y 34) | DATE | — |
| `<IndicadorEnvioDiferido>` | Contingencia tipo 1 | NUM | — |
| `<RNCEmisor>` | RNC del emisor (activo, autorizado) | NUM | — |
| `<FechaEmision>` | Fecha de emisión | DATE | — |
| `<MontoTotal>` | Total en DOP | NUM | 2 |

#### Sección Detalle de Bienes o Servicios

- Máximo **1,000 líneas** por e-CF
- `<PrecioUnitarioItem>`: hasta **4 decimales** (excepción al estándar de 2)
- `<TipoCambio>`: hasta **4 decimales**
- `<Subcantidad>`: hasta **3 decimales**
- Todo lo demás: **2 decimales**
- `<NoLinea>`: correlativo desde 1; no puede haber saltos ni repetidos

#### Sección Totales — cuadratura

```
MontoGravadoTotal = MontoGravadoI1 + MontoGravadoI2 + MontoGravadoI3
TotalITBIS = TotalITBIS1 + TotalITBIS2 + TotalITBIS3
MontoTotal = MontoGravadoTotal + MontoExento + MontoNoFacturable
           + TotalITBIS + impuestosAdicionales ± descuentosRecargosGlobales
```

Ver Módulo 6 para la regla de tolerancia exacta.

### Requerimientos funcionales

**RF-02.1** — Validar la estructura XML contra los XSD oficiales de la DGII antes de firmar. Los XSD son la fuente de verdad para la estructura.

**RF-02.2** — Aplicar la tabla de obligatoriedad (0=no corresponde, 1=obligatorio, 2=condicional, 3=opcional) por tipo de comprobante. Esta lógica vive en el dominio, no en la capa HTTP.

**RF-02.3** — Escapar los siguientes 8 caracteres especiales en todo texto dentro del XML (actualizado abril 2025):

| Carácter | Escape XML |
|---|---|
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | `&gt;` |
| `"` | `&quot;` |
| `'` | `&apos;` |
| `©` | `&#169;` |
| `®` | `&#174;` |
| `€` | `&#8364;` |

**RF-02.4** — Aplicar reglas de formato numérico estrictas:
- 2 decimales: todos los montos, ITBIS, impuestos adicionales
- 4 decimales: `PrecioUnitarioItem`, `PrecioUnitarioItemOtraMoneda`, `TipoCambio`
- 3 decimales: `Subcantidad`
- Sin separador de miles; punto decimal (no coma); sin signo negativo (usar campos negativos específicos del formato)

**RF-02.5** — Ausencia de tags vacíos: un campo sin valor se omite del XML, no se incluye como `<Campo/>` ni `<Campo></Campo>`. El orden de las secciones debe ser exactamente el que define el XSD.

**RF-02.6** — Para tipo 32 < DOP 250,000: generar el RFCE (no el ECF completo) para envío a DGII. El ECF completo se genera y almacena localmente. El RFCE incluye el campo `<TipoIngresos>` (6 códigos) obligatorio.

**RF-02.7** — Generar ARECF firmado al recibir un e-CF de otro contribuyente. El ARECF es la respuesta al endpoint B2B `/fe/recepcion/api/ecf` (ver Módulo 5). Debe estar firmado con nuestro certificado del tenant receptor.

**RF-02.8** — Generar ACECF (aprobación o rechazo comercial) para e-CF de tipos 31, 33, 34, 44, 45 previamente aceptados por DGII.

**RF-02.9** — Generar ANECF con soporte de hasta 10,000 repeticiones de rangos por tipo. Usar `<RncEmisor>` (c minúscula) — casing propio de este formato.

**RF-02.10** — Validar que `<MontoTotal>` de una Nota de Crédito (tipo 34) ≤ `<MontoTotal>` del e-CF modificado referenciado en `<NCFModificado>`.

## 4. Módulo 3 — Firma digital SHA-256 (XMLDSig)

### Descripción

Aplica la firma digital XMLDSig sobre los documentos XML usando el certificado P12 del contribuyente, custodiado en Vault. La firma garantiza autenticidad e integridad ante DGII y el receptor.

### Parámetros de firma (verificados contra PDF DGII)

| Parámetro | Valor correcto |
|---|---|
| `SignatureMethod` | `http://www.w3.org/2001/04/xmldsig-more#rsa-sha256` |
| `DigestMethod` | `http://www.w3.org/2001/04/xmlenc#sha256` |
| `Reference URI` | `""` (firma aplica al documento completo) |
| Transform | `XmlDsigEnvelopedSignatureTransform` |
| C14N (canonicalización) | **Estándar — NO exclusivo**: `c14n(false, false)` |
| `preserveWhitespace` | `false` |

⚠️ **Error crítico de implementación PHP:** Usar `$element->C14N(true, false)` (exclusive C14N) produce una firma que no verifica en DGII, aunque el proceso no lanza error. Debe usarse `$element->C14N(false, false)`. Revisar cualquier implementación PHP de firma.

### Requerimientos funcionales

**RF-03.1** — Implementar firma XMLDSig con los parámetros exactos de la tabla anterior. Cualquier desviación produce firmas que DGII rechaza sin mensaje de error descriptivo.

**RF-03.2** — Incluir el bloque `<KeyInfo>` con `<X509Data>` completo del certificado.

**RF-03.3** — Validar ANTES de firmar:
1. Que el certificado no esté vencido
2. Que el campo `SN` coincida con el RNC/cédula/pasaporte del propietario del tenant
3. Que el XML pase validación XSD
4. Que los cálculos de cuadratura sean correctos (ver RF-06.6)

**RF-03.4** — Una vez firmado, el XML es inmutable. Implementar hash del documento post-firma para auditoría e integridad.

**RF-03.5** — Extraer el `CodigoSeguridad` del `<SignatureValue>`:
- Tomar los **primeros 6 caracteres** del valor Base64 del `<SignatureValue>` (no del hash SHA-256, sino del valor Base64 tal como aparece en el XML firmado)
- Este valor se usa en la URL del QR y en la RI

**RF-03.6** — Validar la firma de los XML recibidos de otros contribuyentes antes de generar el ARECF. Un e-CF con firma inválida debe ser rechazado con HTTP 400 y registrado.

**RF-03.7** — La clave privada nunca sale del módulo de firma. Usar interfaz Vault Transit Engine o equivalente para operaciones criptográficas; la clave privada no toca memoria de la aplicación.

## 5. Módulo 4 — Emisión y envío a DGII

### Descripción

Gestiona el envío de los e-CF firmados a los web services de la DGII y el seguimiento del estado mediante TrackId. Este módulo se comunica con los endpoints DGII (`/api/...`), que son completamente distintos de los endpoints B2B que nosotros exponemos (`/fe/...`).

### Endpoints DGII reales (corregidos)

```
── Autenticación ──────────────────────────────────────────────────────────────
GET  /api/autenticacion/semilla            → Obtener semilla XML
POST /api/autenticacion/validarsemilla     → Validar semilla firmada, obtener JWT

── Emisión ────────────────────────────────────────────────────────────────────
POST /api/facturaselectronicas             → Enviar e-CF (tipos 31,33,34,41,43,44,45,46,47)
POST /api/rfce                             → Enviar RFCE (tipo 32 < DOP 250,000)

── Consulta ───────────────────────────────────────────────────────────────────
GET  /api/consultaresultadoecf?trackId=X   → Estado por TrackId (solo emisor)
GET  /api/consultadirectorio               → URLs B2B de receptores electrónicos
GET  /api/consultaestatusservicio          → Disponibilidad y ventanas de mantenimiento
```

⚠️ Los siguientes endpoints **solo existen en producción (eCF)**, NO en CerteCF:
`consultaestado`, `consultatrackids`, `anulacionrangos`, `consultadirectorio`

### Flujo de emisión (orden obligatorio)

```
1. Obtener token JWT (desde caché Redis o renovar)
2. Generar XML del e-CF
3. Validar XSD + cuadratura de montos
4. Firmar XML (SHA-256, C14N estándar, preserveWhitespace=false)
5. Enviar a DGII:
   - Si tipo 32 < DOP 250k  → POST /api/rfce (RFCE)
   - Si tipo 32 ≥ DOP 250k  → POST /api/facturaselectronicas
   - Cualquier otro tipo    → POST /api/facturaselectronicas
6. Guardar TrackId en DB
7. ¿Debe enviarse al receptor electrónico?
   - Tipos 31, 32(≥250k), 33, 34, 44 → Sí
   - Tipos 41, 43, 45, 46, 47         → No
   - Si Sí: consultar URL del receptor en directorio → enviar XML firmado
8. ¿Receptor no electrónico? → Generar RI (PDF + QR)
9. Programar polling de estado (ver RF-04.3)
```

### Requerimientos funcionales

**RF-04.1** — Toda la lógica de emisión es asíncrona vía Outbox Pattern:
- El endpoint público de la API retorna inmediatamente con `202 Accepted` + ID de seguimiento
- Un worker procesa el outbox en orden y ejecuta los pasos del flujo
- Si el worker falla, el registro en el outbox se reintenta automáticamente
- No usar colas externas (RabbitMQ, SQS) — el outbox sobre la misma DB garantiza atomicidad

**RF-04.2** — Persistir el TrackId devuelto por DGII junto con el e-NCF, timestamp, ambiente y estado en la tabla `comprobantes_ecf`.

**RF-04.3** — Polling de estado post-emisión:
- Primera consulta: 30 segundos después del envío
- Segunda consulta: 5 minutos después (si sigue en proceso)
- Tercera consulta: 30 minutos después (si sigue en proceso)
- Tras 3 consultas sin resultado definitivo: marcar para revisión manual y alertar

**RF-04.4** — Manejar estados de respuesta DGII:
- `Aceptado (1)` — válido; notificar al cliente vía webhook
- `Rechazado (2)` — inválido; registrar motivo, notificar, liberar secuencia
- `En proceso (3)` — continuar polling según RF-04.3
- `Aceptado condicional` — válido; notificar con la observación

**RF-04.5** — Idempotencia: si se recibe dos veces el mismo `NumeroFacturaInterna` del mismo tenant, retornar el resultado del primer e-CF sin crear uno nuevo. Ventana de detección de duplicados: mínimo 24 horas.

**RF-04.6** — Para envío al receptor electrónico: consultar el directorio (`/api/consultadirectorio`) para obtener la URL B2B del receptor. Cachear en Redis con TTL 24 horas en producción.

**RF-04.7** — En caso de error temporal al enviar al receptor electrónico (timeout, 5xx), reintentar con backoff exponencial: 2 min → 10 min → 30 min → 2 h → revisión manual. Los fallos de entrega al receptor NO invalidan el e-CF ante DGII.

## 6. Módulo 5 — Endpoints B2B expuestos (como receptor)

### Descripción

Expone los endpoints públicos HTTPS que todo emisor electrónico debe tener disponibles según la normativa DGII. Estos son los endpoints que **nosotros exponemos** para que otros contribuyentes nos envíen e-CF. Son distintos en estructura y propósito de los endpoints DGII que nosotros consumimos.

### Endpoints B2B que el SaaS expone (por tenant)

| Endpoint | Método | Obligatoriedad | Respuesta |
|---|---|---|---|
| `/fe/autenticacion/api/semilla` | GET | **Opcional** | XML semilla (UUID + timestamp) |
| `/fe/autenticacion/api/validacioncertificado` | POST | **Opcional** | Token JWT |
| `/fe/recepcion/api/ecf` | POST | **Obligatoria** | ARECF firmado (HTTP 200) |
| `/fe/aprobacioncomercial/api/ecf` | POST | **Obligatoria** | HTTP 200 / 400 |

**Diseño multi-tenant:** Cada tenant tiene su propia URL base. Por ejemplo: `https://api.nuestroservicio.com/{tenant_id}/fe/recepcion/api/ecf`. La URL registrada en DGII es la del tenant.

### Requerimientos funcionales

**RF-05.1** — Los endpoints deben ser públicamente alcanzables desde internet, operar en puertos tradicionales (443/HTTPS), y no ser sensibles a mayúsculas/minúsculas en el path.

**RF-05.2** — Flujo al recibir un e-CF (`POST /fe/recepcion/api/ecf`):
1. Si el emisor usa autenticación B2B (opcional): validar token
2. Validar estructura XML contra XSD
3. Validar firma digital del emisor (rechazar con HTTP 400 si inválida)
4. Validar que el tipo de e-CF sea de los que pueden enviarse entre contribuyentes (31, 33, 34, 44)
5. Registrar el e-CF recibido en DB
6. Generar y **retornar el ARECF firmado** (firmado con el certificado del tenant receptor)
7. Notificar internamente al tenant (webhook, evento de dominio)

**RF-05.3** — La autenticación B2B es opcional. Si el emisor solicita la semilla antes de enviar, retornar un UUID nuevo en cada request (no reutilizar semillas).

**RF-05.4** — Solo aceptar los tipos que pueden enviarse entre contribuyentes: 31, 33, 34, 44. Retornar HTTP 400 para tipos 32, 41, 43, 45, 46, 47.

**RF-05.5** — Aprobación comercial (`POST /fe/aprobacioncomercial/api/ecf`): aplica para tipos **31, 33, 34, 44 y 45** (Gubernamental incluido) previamente aceptados por DGII. Retornar HTTP 200 si se procesa correctamente, HTTP 400 en caso de error de estructura o tipo inválido.

**RF-05.6** — El ARECF retornado en la respuesta al endpoint de recepción debe ser generado y firmado sincrónicamente. No diferir la generación del acuse de recibo.

**RF-05.7** — Implementar rate limiting y registro completo de cada e-CF recibido para cumplir con las obligaciones de auditoría como proveedor certificado (Ley 32-23).

## 7. Módulo 6 — Motor de cálculo fiscal

### Descripción

Implementa todas las reglas de cálculo de impuestos establecidas por la DGII. Es un módulo de dominio puro — sin dependencias externas, sin HTTP, completamente determinístico y testeable con precisión decimal.

### Reglas de redondeo

**RF-06.1** — Decimales por campo:
- **2 decimales**: todos los montos de dinero, ITBIS, impuestos adicionales, descuentos, recargos
- **4 decimales**: `PrecioUnitarioItem`, `PrecioUnitarioItemOtraMoneda`, `TipoCambio`
- **3 decimales**: `Subcantidad`

Regla de redondeo: si el tercer decimal ≥ 5, incrementar el segundo en 1 (redondeo estándar). Si < 5, truncar.

### Cálculo de ITBIS

**RF-06.2** — Tres tasas:
- Tasa 1: 18% — `IndicadorFacturacion = 1`
- Tasa 2: 16% — `IndicadorFacturacion = 2`
- Tasa 3: 0% (exento con crédito fiscal) — `IndicadorFacturacion = 3`
- Sin ITBIS (exento sin crédito) — `IndicadorFacturacion = 4`

**RF-06.3** — Si `IndicadorMontoGravado = 1` (precio incluye ITBIS), extraer la base imponible:
`base = PrecioUnitario / (1 + tasaITBIS)`

### Cálculo de ISC — Alcoholes (códigos 006-039)

**RF-06.4** — Para bebidas alcohólicas:
1. `precioSinITBIS = PrecioRef / (1 + tasaITBIS)`
2. `baseISC = (precioSinITBIS - (MontoISCEspecifico / (CantidadRef × CantidadItem))) / (1 + tasaISCAdValorem)`
3. `MontoISCAdValorem = baseISC × CantidadItem × CantidadRef × tasaAdValorem`
4. `MontoISCEspecifico = TasaImpuestoAdicional × GradosAlcohol × CantidadRef × Subcantidad × CantidadItem`

### Cálculo de ISC — Cigarrillos (códigos 040-049)

**RF-06.5**:
1. `MontoISCEspecifico = CantidadItem × CantidadRef × TasaImpuestoAdicional`
2. `MontoISCAdValorem = ((PrecioRef/(1+ITBIS)) - TasaISCEspecifico) / (1 + tasaAdValorem) × CantidadItem × CantidadRef × tasaAdValorem`

### Regla de tolerancia de cuadratura (CORREGIDA)

**RF-06.6** — Tolerancia de ±1 por línea:
- Por cada línea de detalle, la diferencia entre `MontoItem` calculado y el suministrado puede ser ≤ ±1 unidad
- **Tolerancia global = número de líneas del e-CF** (no ±1 peso global)
- Si la diferencia global excede la tolerancia: el e-CF es **válido**, se envía a DGII, y DGII lo marcará como **aceptado condicional** — no es una causa de rechazo por el sistema
- La validación previa sirve para **anticipar** ese resultado y notificar al cliente, no para bloquear el envío

⚠️ El sistema NO debe rechazar un e-CF por exceder la tolerancia. La decisión es de DGII. El sistema valida, calcula la diferencia, registra la advertencia y procede.

### Regla NC tipo 34 — 30 días (IndicadorNotaCredito)

**RF-06.7** — Al emitir una Nota de Crédito tipo 34:
- Si `FechaEmision NC` - `FechaEmision eCF original` ≤ 30 días → `IndicadorNotaCredito = 1`
- Si > 30 días → `IndicadorNotaCredito = 2`
- Este campo afecta el tratamiento fiscal; debe calcularse automáticamente.

### Descuentos y recargos globales

**RF-06.8** — Distribuir proporcionalmente a cada línea según `MontoItem / SumaMontoItems`. Si `IndicadorNorma10-07 = 1`, el descuento no se rebaja del monto gravado ITBIS Tasa 1.

### Otra moneda

**RF-06.9** — Calcular primero en DOP, luego dividir por `TipoCambio` del Banco Central para campos `*OtraMoneda`.

## 8. Módulo 7 — Gestión de secuencias e-NCF

### Descripción

Administra el inventario de secuencias de comprobantes fiscales electrónicos autorizadas por la DGII, garantizando asignación única (lock pesimista), orden y control de vencimiento.

### Estructura del e-NCF

`[Serie E-Z (excl. P)] + [Tipo 2 dígitos] + [Secuencial 10 dígitos]`

Ejemplo: `E310000000001` (Serie E, Tipo 31, Secuencial 1)

Vencimiento: **31 de diciembre del año siguiente** a la autorización.
**Excepción:** tipos 32 y 34 — NO tienen `FechaVencimientoSecuencia`.

### Reglas por ambiente

| Ambiente | Rango de secuencias | Reutilizable tras rechazo |
|---|---|---|
| TesteCF | Configurable | Sí (ambiente de pruebas) |
| **CerteCF** | **1 a 10,000,000 por tipo** | **No — nueva secuencia obligatoria** |
| eCF (producción) | Según autorización DGII | No |

### Requerimientos funcionales

**RF-07.1** — Almacenar rangos autorizados con: `tenant_id`, `tipo_ecf`, `serie`, `desde`, `hasta`, `siguiente`, `fecha_vencimiento`, `ambiente`, `activo`.

**RF-07.2** — Asignación atómica con bloqueo pesimista (SELECT FOR UPDATE o equivalente). Bajo alta concurrencia, garantizar que dos requests simultáneos del mismo tenant nunca obtengan la misma secuencia.

**RF-07.3** — Alertar cuando el stock caiga por debajo del 20% del rango autorizado por tipo.

**RF-07.4** — Bloquear emisión con secuencias vencidas. La validación de vencimiento ocurre antes del lock.

**RF-07.5** — Ciclo de vida de cada secuencia asignada:
`disponible → asignada → firmada → enviada_dgii → aceptada | rechazada`

Si rechazada en CerteCF: marcar como no reutilizable, no incrementar el siguiente pointer para esa secuencia (la secuencia queda quemada).

**RF-07.6** — Soportar múltiples series activas por tipo (E, F, G... Z, excl. P). La asignación debe ser configurable por ambiente (para CerteCF el sistema inicia siempre desde 1).

```sql
CREATE TABLE secuencias_ecf (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id        UUID NOT NULL REFERENCES tenants(id),
  tipo_ecf         SMALLINT NOT NULL,
  serie            CHAR(1) NOT NULL,
  desde            BIGINT NOT NULL,
  hasta            BIGINT NOT NULL,
  siguiente        BIGINT NOT NULL,
  fecha_vencimiento DATE,                 -- NULL para tipos 32 y 34
  ambiente         VARCHAR(10) NOT NULL,
  activo           BOOLEAN DEFAULT TRUE,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CONSTRAINT uk_siguiente UNIQUE (tenant_id, tipo_ecf, serie, ambiente)
);
```

## 9. Módulo 8 — Anulaciones y notas de crédito

### Descripción

Gestiona las dos vías para corregir o invalidar un e-CF, según si ya fue comunicado a DGII o al receptor. La bifurcación es estricta y no admite mezcla.

### Regla de decisión

```
¿El e-CF fue enviado a DGII o al receptor?
├── NO → Anulación de e-NCF (ANECF) — XML de anulación de secuencias
└── SÍ → Nota de Crédito Electrónica (Tipo 34) referenciando el e-NCF original
```

### Requerimientos funcionales

**RF-08.1** — ANECF (anulación de secuencias no enviadas):
- `<RncEmisor>` (c minúscula — casing específico del ANECF, diferente al resto de formatos)
- Hasta 10 tipos diferentes de e-CF por documento de anulación
- Hasta 10,000 rangos por tipo
- Rangos deben ser consecutivos; `desde ≤ hasta`; misma serie y tipo en todo el rango
- Antes de generar: verificar en DB que las secuencias pertenecen al tenant y tienen estado `asignada` o `firmada` (nunca `enviada_dgii`)

**RF-08.2** — Nota de Crédito (tipo 34):
- `<NCFModificado>` = e-NCF del e-CF original que se revierte
- `<MontoTotal>` NC ≤ `<MontoTotal>` del e-CF original
- Calcular `<IndicadorNotaCredito>` según regla de 30 días (ver RF-06.7)
- Flujo completo de firma y envío (igual que cualquier e-CF tipo 34)

**RF-08.3** — Registrar en auditoría: motivo, usuario, timestamp, e-NCF afectado.

**RF-08.4** — Marcar automáticamente las secuencias anuladas como `anulada` en el inventario; no reutilizar nunca esas secuencias.

## 10. Módulo 9 — Representación impresa (RI) y código QR

### Descripción

Genera la representación impresa del e-CF conforme al Decreto 254-06 y Norma General 06-2018. El código QR es una URL de verificación en los servidores de DGII; su construcción tiene reglas exactas de encoding.

### URLs del QR (verificadas contra documentación DGII)

#### e-CF normal (tipos distintos de tipo 32 < 250k)
```
https://ecf.dgii.gov.do/consultatimbre
  ?RncEmisor={RNC_EMISOR}
  &RncComprador={RNC_COMPRADOR}
  &ENCF={ENCF}
  &FechaEmision={dd-MM-yyyy}
  &MontoTotal={MONTO}
  &FechaFirma={dd-MM-yyyy%20HH%3Amm%3Ass}
  &CodigoSeguridad={CODIGO}
```

#### RFCE (tipo 32 < DOP 250,000)
```
https://fc.dgii.gov.do/consultatimbrefc
  ?RncEmisor={RNC_EMISOR}
  &ENCF={ENCF}
  &MontoTotal={MONTO}
  &CodigoSeguridad={CODIGO}
```

### Reglas de URL encoding para el QR

Los parámetros de la URL deben aplicar percent-encoding a caracteres de 30+ código ASCII. Casos más frecuentes:

| Carácter | Encoding |
|---|---|
| espacio ` ` | `%20` |
| `:` | `%3A` |
| `/` | `%2F` |
| `@` | `%40` |
| `+` | `%2B` |

La `FechaFirma` contiene espacios y dos puntos → siempre requiere encoding: `dd-MM-yyyy%20HH%3Amm%3Ass`.

### Requerimientos funcionales

**RF-09.1** — `CodigoSeguridad` = **primeros 6 caracteres** del valor Base64 del `<SignatureValue>` tal como aparece en el XML firmado. No es el hash SHA-256; es el string Base64 del valor de firma.

**RF-09.2** — `FechaHoraFirma` en zona horaria **GMT-4 (hora dominicana)**, formato `dd-MM-yyyy HH:mm:ss`. Esta es la `FechaHoraFirma` del XML; la URL del QR la recibe con encoding.

**RF-09.3** — El QR debe ser versión 8 o superior con corrección de error nivel M mínimo, suficiente para la longitud de la URL más larga esperada.

**RF-09.4** — La RI debe contener todos los campos del Decreto 254-06: datos del emisor, datos del receptor, e-NCF, fecha de emisión, fecha de vencimiento de secuencia (si aplica), detalle de bienes/servicios, totales, ITBIS desglosado, código QR y código de seguridad visible.

**RF-09.5** — En contingencia tipo 1, la RI debe incluir la leyenda obligatoria prescrita verbatim por DGII. No parafrasear. Esta leyenda distingue un comprobante de contingencia de uno normal.

**RF-09.6** — Generar RI en PDF. Soportar al menos dos layouts: carta (8.5×11) y POS (80mm de ancho). La paginación automática aplica cuando el e-CF supera las líneas que caben en una página.

**RF-09.7** — El PDF puede enviarse por correo electrónico al receptor si se dispone de `<CorreoComprador>`.

## 12. Módulo 11 — Contingencia (Decreto 587-24)

### Descripción

Permite la continuidad operativa cuando los servicios DGII no están disponibles. Existen **tres tipos de contingencia** con reglas y obligaciones distintas. Tratarlos como un flujo único es incorrecto.

### Tipo 1 — Falta de conectividad (más común)

**Causa:** DGII inaccesible por problemas de red del emisor o de DGII.
**Ventana:** **72 horas** desde el inicio del evento.
**Notificación a DGII:** **No requerida.**

**RF-11.1** — Detectar tipo 1 cuando el endpoint de estatus (`/api/consultaestatusservicio`) no responde tras 3 intentos con backoff.

**RF-11.2** — En contingencia tipo 1: permitir emisión local. El e-CF se genera, firma localmente y almacena con estado `contingencia_pendiente`. Se asigna secuencia normal; se incluye `<IndicadorEnvioDiferido>1</IndicadorEnvioDiferido>` en el XML.

**RF-11.3** — La RI emitida en contingencia tipo 1 **debe incluir la leyenda obligatoria** (texto exacto según normativa DGII — no parafrasear). Esta RI es diferente a la de modo normal.

**RF-11.4** — Al restaurar conectividad: enviar automáticamente los e-CF pendientes en orden cronológico. Plazo máximo: 72 horas desde la emisión en contingencia.

### Tipo 2 — Imposibilidad técnica del emisor

**Causa:** El sistema del emisor no puede generar e-CF (falla del software/hardware).
**Ventana:** **15 días calendario** desde el inicio.
**Notificación a DGII:** **Obligatoria vía OFV** (Oficina Virtual).

**RF-11.5** — Al activar contingencia tipo 2: notificar automáticamente a DGII vía OFV. El sistema debe proporcionar la interfaz para que el operador complete la notificación.

**RF-11.6** — Al salir de contingencia tipo 2: el emisor tiene **30 días** para regularizar los comprobantes emitidos en ese período. Los e-CF de regularización van **solo a DGII** (no al receptor electrónico).

### Tipo 3 — Otros supuestos

Consultar el Decreto 587-24 para los supuestos específicos. Implementar con la misma estructura de estados pero con las reglas propias del tipo.

### Reglas comunes

**RF-11.7** — Máquina de estados por e-CF:
`normal | contingencia_pendiente | regularizando | regularizado | error`

**RF-11.8** — Registrar cada período de contingencia: `tipo`, `inicio`, `fin`, `cantidad_ecf_emitidos`, `notificacion_dgii` (timestamp si aplica).

**RF-11.9** — Notificar al tenant cuando entra y sale de contingencia, con el tipo de contingencia activado.

## 14. Módulo 13 — Infraestructura y resiliencia

### Descripción

Define la infraestructura de soporte del SaaS. La decisión arquitectural central es el **Outbox Pattern sobre la base de datos relacional** en lugar de una cola de mensajes externa. Esto garantiza atomicidad sin la complejidad operativa de RabbitMQ/SQS en las primeras etapas.

### Componentes

#### Base de datos relacional

Tablas principales:

```
tenants              → Contribuyentes registrados en el SaaS
certificados_ecf     → Metadata de certificados (no el P12; ruta en Vault)
secuencias_ecf       → Rangos autorizados + estado de asignación
comprobantes_ecf     → e-CF emitidos y recibidos (estado, trackId, ambiente)
eventos_ecf          → Historial inmutable de cambios de estado por e-CF
outbox               → Cola de trabajo pendiente (patrón Outbox)
contingencias        → Períodos de contingencia con tipo, inicio, fin
logs_comunicacion    → Log de cada llamada a DGII (request, response, ms)
webhooks_config      → URLs y secretos HMAC por tenant
webhooks_entregas    → Historial de entregas y reintentos de webhooks
```

#### Outbox Pattern (reemplaza RabbitMQ/SQS)

```
outbox {
  id             UUID PRIMARY KEY,
  tenant_id      UUID NOT NULL,
  tipo           VARCHAR(50) NOT NULL,  -- emision_ecf | envio_receptor | webhook | ...
  payload        JSONB NOT NULL,
  estado         VARCHAR(20) NOT NULL DEFAULT 'pendiente',
  intentos       INT NOT NULL DEFAULT 0,
  proximo_intento TIMESTAMPTZ,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  procesado_at   TIMESTAMPTZ
}
```

El worker de outbox es un proceso de background que:
- Consulta registros `pendiente` con `proximo_intento ≤ NOW()`
- Procesa en orden `created_at ASC` por tenant
- Marca `procesado` al éxito; calcula backoff exponencial en fallo
- Al pasar a una cola externa (fase futura), el outbox es el productor confiable

#### Vault de secretos (HashiCorp Vault o equivalente)

- Almacenar certificados P12 cifrados, con acceso auditado por `tenant_id`
- Vault Transit Engine para operaciones criptográficas (la clave privada nunca sale)
- Rotación automática de credenciales de DB
- Nunca almacenar secretos en variables de entorno en texto plano en producción

#### Caché (Redis)

- Tokens JWT DGII por tenant+ambiente (TTL = expiración - 5min)
- Directorio de facturadores (TTL = 24h en producción)
- Claves de idempotencia (TTL = 24h)
- Semillas B2B activas (TTL = 5 minutos)

### Requerimientos no funcionales

- **Disponibilidad**: 99.9% (≤ 8.7 horas de downtime/año) — requisito de proveedor DGII
- **Latencia**: emitir un e-CF retorna `202 Accepted` en < 500ms (p95); resultado final en < 5 segundos (p95)
- **Throughput**: diseñar para 100 e-CF/segundo por tenant desde el inicio; escalar horizontal vía workers adicionales
- **Retención**: todos los e-CF conservados mínimo 10 años (normativa tributaria)
- **Backup**: respaldo diario con retención 30 días; point-in-time recovery habilitado

## 15. Módulo 14 — Seguridad

### Descripción

La seguridad es un requisito de proveedor certificado (Ley 32-23). No es opcional ni diferible.

### Requerimientos

**RF-14.1** — TLS 1.2+ en todas las comunicaciones. Validar certificado del servidor DGII. Rechazar conexiones a endpoints DGII con certificados inválidos o vencidos.

**RF-14.2** — Cifrado en reposo de todos los datos sensibles: certificados (en Vault), tokens (Redis cifrado), datos fiscales (DB cifrada).

**RF-14.3** — Multi-tenant estricto: Row Level Security (RLS) en PostgreSQL o schemas separados por tenant. Ninguna query puede acceder a datos de otro tenant.

**RF-14.4** — Auditoría completa e inmutable: cada acción de emitir, anular, consultar, recibir debe registrar `tenant_id`, `usuario_id`, `ip_origen`, `timestamp`, `resultado`. Los logs de auditoría son append-only, almacenados en tabla separada sin posibilidad de UPDATE/DELETE.

**RF-14.5** — Control de acceso por roles (RBAC):

| Rol | Permisos |
|---|---|
| `admin_tenant` | Configuración, certificados, secuencias, webhooks |
| `emisor` | Emitir, consultar propios, descargar RI |
| `consultor` | Solo lectura de comprobantes y estados |
| `admin_sistema` | Acceso total (solo operadores del SaaS) |

**RF-14.6** — Rate limiting y protección contra fuerza bruta en todos los endpoints de autenticación. Bloqueo temporal tras 5 intentos fallidos.

**RF-14.7** — Cumplimiento Ley 32-23 (Protección de Datos): política de privacidad, contratos de procesamiento con clientes, procedimiento de respuesta a incidentes de datos. Como proveedor certificado custodiando datos fiscales, esto es una obligación legal explícita.

**RF-14.8** — Escaneo automático de dependencias vulnerables en CI/CD (OWASP Dependency Check o Snyk).

## 16. Módulo 15 — Panel de administración y monitoreo

### Requerimientos funcionales

**RF-15.1** — Dashboard principal con métricas en tiempo real:
- e-CF emitidos hoy / semana / mes (por tipo y por tenant)
- Tasa de aceptación / aceptado condicional / rechazado
- Estado de conectividad DGII (verde/amarillo/rojo con latencia)
- Stock de secuencias disponibles con alertas de umbral por tipo
- e-CF en contingencia pendientes de envío

**RF-15.2** — Listado de comprobantes con filtros por: fecha, tipo, estado, receptor, ambiente; búsqueda por e-NCF o número interno.

**RF-15.3** — Vista detalle de cada e-CF: XML generado, XML firmado, XML del ARECF recibido, historial completo de estados con timestamps, respuesta DGII, aprobación comercial si aplica.

**RF-15.8** — Log de comunicaciones DGII: cada llamada, URL, código HTTP, tiempo de respuesta, payload (sin datos sensibles). Retenido 90 días mínimo.

## 17. Hoja de ruta de implementación

### Consideraciones estratégicas

Para convertirse en proveedor certificado, la secuencia es:
1. Completar el software
2. Certificarse como emisor electrónico (Track B — 15 pasos con DGII)
3. Certificar 3 primeros clientes (Track B individualmente)
4. Presentar FI-GDF-017 presencialmente en DGII + esperar 10 días hábiles
5. Obtener certificación como proveedor → nuevos clientes usan Track A (simplificado)

Las fases de implementación deben culminar en la ventana de certificación antes de noviembre 2026.

## 18. Checklist de certificación DGII

### Track B — Proceso de 15 pasos (para nosotros y para los primeros 3 clientes)

#### Comunicación y estructura
- [ ] HTTPS en todos los endpoints públicos (443)
- [ ] Endpoints B2B alcanzables desde internet (URLs registradas en DGII activas)
- [ ] Endpoints no sensibles a mayúsculas/minúsculas
- [ ] Endpoint de recepción retorna ARECF firmado en el body

#### Autenticación
- [ ] `GET /api/autenticacion/semilla` → XML semilla válido
- [ ] `POST /api/autenticacion/validarsemilla` → Token JWT obtenido
- [ ] Renovación proactiva de token (5 min antes de expirar)
- [ ] Certificado emitido por prestadora autorizada por INDOTEL
- [ ] Campo `SN` del certificado = RNC/cédula del propietario

#### Firma digital
- [ ] Algoritmo SHA-256 con XMLDSig
- [ ] C14N **estándar** (NO exclusivo) — `c14n(false, false)`
- [ ] `preserveWhitespace = false`
- [ ] `Reference URI=""` (firma al documento completo)
- [ ] XML inmutable post-firma

#### Generación de XML
- [ ] Validación XSD para todos los tipos implementados
- [ ] 8 caracteres especiales escapados correctamente (incluyendo ©, €, ®)
- [ ] `FechaVencimientoSecuencia` ausente en tipos 32 y 34
- [ ] `RNCComprador` en tipo 32 solo si ≥ DOP 250,000
- [ ] Regla de redondeo correcta (4d `PrecioUnitario`, 3d `Subcantidad`)
- [ ] `ANECF` usa `<RncEmisor>` (c minúscula)
- [ ] `TipoIngresos` presente en el RFCE

#### Tolerancia de cuadratura
- [ ] Tolerancia por línea ±1; tolerancia global = número de líneas
- [ ] e-CF con diferencia dentro de tolerancia: enviar a DGII (aceptado condicional esperado)
- [ ] Sistema NO bloquea envío por cuadratura; solo valida y advierte

#### Pruebas de datos Track B (Paso 2)
- [ ] 21 e-CFs generados con el dataset Excel que provee DGII
- [ ] Secuencias CerteCF (rango 1–10M, no reutilizables)
- [ ] Si algún e-CF es rechazado: nueva secuencia, no reutilizar la anterior

#### Representación impresa (Paso 6 Track B)
- [ ] URL QR correcta: `https://ecf.dgii.gov.do/consultatimbre` (7 params, todos con encoding)
- [ ] URL QR RFCE: `https://fc.dgii.gov.do/consultatimbrefc` (4 params)
- [ ] `CodigoSeguridad` = primeros 6 caracteres Base64 del `<SignatureValue>`
- [ ] `FechaHoraFirma` en GMT-4, con URL encoding en el QR
- [ ] QR versión 8+
- [ ] Leyenda de contingencia presente solo en RI de contingencia (tipo 1)
- [ ] Layout carta y POS 80mm generados

#### Aprobaciones comerciales (Paso 3 Track B)
- [ ] ACECF generado correctamente para tipos 31, 33, 34, 44, 45
- [ ] Dataset de aprobaciones comerciales provisto por DGII

#### Pruebas de comunicación B2B (Paso 12 Track B)
- [ ] `POST /fe/recepcion/api/ecf` recibe e-CF y retorna ARECF firmado
- [ ] `POST /fe/aprobacioncomercial/api/ecf` retorna HTTP 200

#### Simulaciones (Paso 14 Track B)
- [ ] Simulación de tipo 31 completada
- [ ] Simulación de tipo 32 completada (y RFCE para < 250k)
- [ ] Simulación de tipo 33 completada
- [ ] Simulación de tipo 34 completada
- [ ] Demás tipos según requerimiento DGII

#### Secuencias y módulo de gestión
- [ ] Asignación atómica bajo concurrencia (lock pesimista)
- [ ] Pool de secuencias CerteCF separado de producción
- [ ] Punto de inicio configurable por ambiente

#### Contingencia
- [ ] Tipo 1: leyenda obligatoria en RI, sin notificación a DGII, 72h de ventana
- [ ] Tipo 2: notificación OFV, 15 días, regularización 30 días solo a DGII
